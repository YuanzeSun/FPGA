# CPU 怎样执行一条指令

这份实现把控制逻辑放在 `rv32_core.v` 中，组合译码与运算由子模块完成。一条指令经过多个时钟，当前指令完成后才取下一条。

## 三个运行状态

1. FETCH：通过总线读取 PC 指向的 32 位指令，收到应答后保存到 `instr`。
2. EXEC：译码，读取两个源寄存器，计算结果。普通运算此时写回寄存器并更新 PC。
3. MEMORY：只有加载和存储指令进入这里。保持请求，等待存储器应答，然后写回加载结果、PC 加 4。

普通指令的 PC 加 4；跳转和成立的分支使用计算出的目标地址。HALT 是异常后的停机状态。

例如 `add x3,x1,x2`：译码器选择加法，寄存器组提供 x1、x2，ALU 输出它们的和。EXEC 完成时把结果写给 x3，再取下一条指令。

## 总线为什么需要 ready

CPU 输出 `mem_valid`、地址、写数据和四个字节写使能。存储器用 `mem_ready` 应答，并提供读数据或错误。等待期间 CPU 保持请求不变；总线慢一些也可以运行。

读取字节或半字时，核心先读取对应的 32 位字，再移位、截取并按需要符号扩展。存储时移位写数据，并只打开需要的字节写使能。多字节访问需要自然对齐。

## 哪些东西放在哪里

PC、当前指令、访存期间保存的地址等，都是核心内部寄存器。x0～x31 属于程序能直接使用的寄存器组。它们与片上 RAM 是不同的存储位置。

LED 由 C 程序写 GPIO 地址控制。CPU 核心本身不知道 LED、串口或开发板引脚；这些由 SoC 和顶层连接，因此也可以换成别的外设。

## 支持范围

| 类别 | 指令 |
| --- | --- |
| 高位立即数 | LUI、AUIPC |
| 跳转 | JAL、JALR |
| 分支 | BEQ、BNE、BLT、BGE、BLTU、BGEU |
| 加载 | LB、LH、LW、LBU、LHU |
| 存储 | SB、SH、SW |
| 立即数运算 | ADDI、SLTI、SLTIU、XORI、ORI、ANDI、SLLI、SRLI、SRAI |
| 寄存器运算 | ADD、SUB、SLL、SLT、SLTU、XOR、SRL、SRA、OR、AND |
| 顺序与环境 | FENCE、ECALL、EBREAK |

FENCE 不需要额外动作，因为当前系统按顺序完成每一次访存。ECALL 和 EBREAK 交给执行环境处理；本版执行环境选择记录原因并停止。

异常原因码采用 RISC-V 常见编号：0 指令地址未对齐、1 取指访问错误、2 非法指令、3 断点、4/6 加载/存储未对齐、5/7 加载/存储访问错误、11 ECALL。原因和附加值由调试端口导出，没有提供异常向量、CSR 或 MRET 返回机制。

## 测试怎么看

`scripts/test_isa.py` 有一份独立的 Python 指令解释器。相同的程序分别由解释器和 RTL 执行，对照每条完成指令的 PC、指令字、目标寄存器及结果，再比较 RAM 和异常状态。

三组随机程序使用固定种子，可以复现；定向用例检查跳转对齐、访存错误、非法指令等。`sim/core_tb.v` 会给总线加入不同等待周期，并检查等待时请求保持稳定。

`sim/soc_tb.v` 则让实际核心运行 GCC 生成的 C 固件，通过真正的 UART 位流收发验证自检和交互。仿真只加快了外设计时器的增长，CPU 指令和 UART 分频与实机相同。
