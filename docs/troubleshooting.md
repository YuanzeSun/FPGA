# 排错

## 下载器没有找到板子

先看 Windows 设备管理器，再运行 `--scan-cables F`。关闭串口程序和其他下载器实例，确认没有上次中断后留下的进程，然后重新读取器件 ID。

枚举位置为 0、打不开接口或出现 USB 描述符失败时，先恢复 USB 连接。可以尝试关闭软件后重新枚举；软件恢复不一定有效，必要时才拔插。未读到正确 ID 前不要继续写入。

本机曾执行 Windows 设备重启，命令虽返回 0，USB 却没有恢复，最后靠拔插解决。因此不把设备重启列为固定操作。

## Flash 写入很慢

本机曾用 Programmer 1.9.12.04 + FT2CH 等待数十分钟仍未完成，换成 1.9.11.02 + USB Debugger A 后，同一份位流约 8 秒写完。优先核对 [验证基线](../records/verified-baseline.md) 中的组合。

版本和 Cable 模式当时一起更换，无法单独判定哪项是主因。也不能只归因于 Verify：当时去掉 Verify 后仍然很慢。发生异常时保存进度和耗时，停止盲目重试；取消写入后，先恢复连接再决定是否重写。

## 到了 100% 仍报错

区分“设备已经运行”和“工具正常完成”。检查退出码、错误文本、User Code 和状态位，保留异常记录。本机早期原始位流缺少 Programmer 所需元数据，补充注释后加载正常；处理方法见 [日常开发](development.md)。

有些连接错误也会返回退出码 0，因此不能仅凭退出码判断成功。

## 串口没输出或乱码

依次检查实际 COM 号、端口是否被占用、当前位流是否包含 UART、CPU 时钟与串口分频是否一致，再检查 TX/RX 管脚和复位。两端都是 115200，不代表硬件分频一定正确。

如果只看到一批旧文字，发送一条带本次标记的查询，确认有新应答。下载与串口测试分开进行。

## LED 和预期不同

先区分六颗用户 LED 与下载器附近的独立状态灯。用户 LED 低电平点亮；独立灯的亮灭不能直接当作用户程序是否运行的依据。

如果断电后又回到旧实验，检查是否只加载了 SRAM。这是 SRAM 调试的正常行为。

## 时序或资源不通过

保留失败日志，检查时钟约束、复位和映射选项。超容量或时序不满足的候选先在电脑上解决，不靠反复下载验证。CPU 的快速乘法器、存储器映射等选项会明显改变资源占用。
